# Rust Linux Panel — Codex Implementation Plan

## 0. Mission and non-negotiable constraints
Build a lightweight, self-hosted multi-node Linux management panel inspired by 3x-ui, focused initially on managing Xray-core. Start from an empty repository and implement in small, testable phases.

- Production must not require Node.js, Caddy, Nginx, PostgreSQL, Redis, Docker, or Kubernetes.
- Frontend: React + TypeScript + Vite + Ant Design. Node.js is permitted only in CI/development to build assets.
- Server: Rust + Axum + Tokio + SQLite/SQLx; embed Vite dist using rust-embed.
- Agent: Rust + Tokio; outbound authenticated WebSocket to Server; manage Linux/systemd and Xray-core.
- Installer: a separate, nonresident Rust CLI using clap + dialoguer; a small reviewed shell bootstrap downloads and verifies it.
- Deployment: systemd, Linux x86_64 and aarch64; first supported distro family Debian/Ubuntu, with explicit capability detection.
- Releases: GitHub Actions build web first, then Rust server/agent/installer; publish checksums, signed artifacts, systemd templates, bootstrap script.
- No arbitrary remote shell, generic file editing, user-provided systemd unit names, or uncontrolled root execution.
- All sensitive credentials must be protected; use least privilege and audit administrative changes.
- Keep a single Cargo workspace with four crates at first: server, agent, common, installer. Split further only when needed.
- Deliver a working MVP before advanced features. No mock behavior disguised as production implementation.

## 1. High-level architecture

Browser --HTTPS--> panel-server (Axum: embedded React SPA, REST API, WebSocket, SQLite)
                               ^
                               | outbound WSS + node authentication
                               |
                         panel-agent (unprivileged network/telemetry/control loop)
                               |
                  allowlisted privileged operations (separate short-lived helper/installer)
                               |
                       systemd / files / Xray-core

The central server is the source of truth for desired node configurations. The agent is the source of truth for observed status. Xray remains a separately managed binary/service. Agent reconnects and reconciles after outages. Local running Xray keeps working if control plane is unreachable.

Security boundary: the privileged installer/helper is not a generic command executor. Implement fixed operations, strict argument validation, canonical path checks, explicit ownership, and a limited authorization mechanism. Do not grant the entire long-running agent root unless documented as a temporary dev-only shortcut, never the production default.

## 3. Domain model and database

Use SQLite WAL, foreign keys, busy timeout, migrations, a small SQLx connection pool. Single writer server instance for MVP. Never store high-frequency telemetry as individual rows indefinitely.

Tables (minimum):
- admins: id, username unique, password_hash, created_at, disabled_at
- sessions: id, admin_id, token_hash, expires_at, revoked_at, created_at
- nodes: id, name, status, agent_version, os, arch, last_seen_at, created_at, revoked_at
- enrollments: id, token_hash, expires_at, consumed_at, node_id, created_at
- node_credentials: node_id, credential_hash or certificate metadata, issued_at, expires_at, revoked_at
- inbounds: id, node_id, name, protocol, listen_address, listen_port, settings_json, enabled, created_at, updated_at
- clients: id, display_name, protocol_identity_json, enabled, expiry_at, quota_bytes, created_at
- client_assignments: id, client_id, inbound_id, enabled, unique(client_id,inbound_id)
- config_revisions: id, node_id, revision integer, desired_config_json, content_hash, status, created_at, applied_at; unique(node_id,revision)
- tasks: id, node_id, operation, payload_json, idempotency_key, desired_revision, status, attempt_count, created_at, deadline_at, finished_at, error_code, error_message
- traffic_aggregates: node_id, client_id nullable, bucket_start, uplink_bytes, downlink_bytes, unique composite key
- audit_logs: id, actor_id nullable, node_id nullable, action, target, result, created_at, metadata_json (redacted)
- install_metadata: optional version/status details; node-local manifest belongs on node, not central DB.

Explicitly decide whether clients are globally identified or per-inbound. Use stable IDs; validate referential integrity. Store timestamps UTC. For credential-bearing Xray config, limit read access, avoid logs and redact API output. Implement retention policy for telemetry and audit.

## 4. API design

Version REST endpoints under `/api/v1` and reserve `/agent/v1/connect` for WSS. Do not let SPA fallback swallow unknown API routes.

Auth:
- POST /api/v1/auth/login
- POST /api/v1/auth/logout
- GET  /api/v1/auth/me

Nodes:
- GET/POST /api/v1/nodes
- GET/PATCH/DELETE /api/v1/nodes/:id
- POST /api/v1/nodes/enrollments (returns one-time token only once)
- GET /api/v1/nodes/:id/status
- GET /api/v1/nodes/:id/metrics

Xray:
- GET/POST /api/v1/nodes/:id/inbounds
- GET/PATCH/DELETE /api/v1/inbounds/:id
- GET/POST /api/v1/clients
- GET/PATCH/DELETE /api/v1/clients/:id
- POST /api/v1/inbounds/:id/clients/:client_id
- DELETE /api/v1/inbounds/:id/clients/:client_id
- GET /api/v1/nodes/:id/config/revisions
- POST /api/v1/nodes/:id/config/apply
- GET /api/v1/nodes/:id/traffic

Operations:
- POST /api/v1/nodes/:id/xray/install
- POST /api/v1/nodes/:id/xray/upgrade
- POST /api/v1/nodes/:id/xray/restart
- POST /api/v1/nodes/:id/xray/uninstall
- GET /api/v1/tasks/:id
- GET /api/v1/audit

Admin authentication: password hashed with Argon2id; use secure, HttpOnly, SameSite cookies, CSRF protection for state-changing requests, rate limiting, session revocation and short expiration. No default hardcoded admin password. Installer initializes first admin securely. Add RBAC only when multi-admin is required; MVP can have a single admin role.

Define uniform JSON envelope for errors with machine-readable error codes; use request IDs and validation. Document OpenAPI or maintain checked contract types. Generate TS types from Rust using ts-rs or an equivalent tested mechanism.

## 5. Agent protocol

WebSocket messages are JSON tagged unions, versioned and bounded in size. Suggested envelope:

```
{
  "version": 1,
  "message_id": "uuid",
  "kind": "task|task_result|heartbeat|metrics|config_status|hello|ack",
  "node_id": "uuid",
  "sent_at": "RFC3339 UTC",
  "payload": {}
}
```

Agent connects outbound over WSS. Enroll with short-lived, single-use token, then use a durable per-node credential (prefer mutually authenticated TLS when operationally feasible; otherwise rotateable node secret with server-side hash and TLS). Bind node identity to connection; never trust client-supplied node_id alone. Never send enrollment tokens in URL query strings. Ensure credentials are not exposed to browser routes.

Implement ping/pong, reconnect with exponential backoff and jitter, message size limit, connection authentication, heartbeat every ~15–30 seconds, task ACK and result, task deadline, idempotency, bounded queues and explicit offline status. Persist server-side tasks before dispatch. On reconnect, reconcile desired revision, not just replay every old task. A task must not execute twice due to duplicate delivery. Use an operation enum instead of arbitrary shell commands.

Task examples: XrayInstall{version}, XrayUpgrade{version}, XrayUninstall{remove_data}, XrayApplyConfig{revision,hash,config}, XrayRestart, XrayStatus, CollectMetrics. Validate all fields and enforce local authorization. No remote arbitrary command task.

## 6. Agent Linux and Xray responsibilities

- systemd: use zbus/D-Bus where practical; allowlist only owned units (`panel-agent.service`, `xray.service`), use a narrowly scoped privileged mechanism for operations requiring root.
- metrics: procfs/sysinfo, CPU/memory/disk/network, bounded periodic sampling; report summarized metrics. No unbounded buffers.
- Xray binary: download from official verified releases, verify signed release/checksum against trusted release metadata, maintain versioned installation directory and current symlink; do not overwrite a pre-existing unowned Xray installation.
- Xray config: typed Rust model and serde serialization, validate supported protocols (start with VLESS + REALITY), generate complete config, validate using installed Xray binary's test mode, atomically write file with restrictive permissions, backup last known-good, apply/restart, health-check, rollback on failure.
- Xray runtime API: enable StatsService/HandlerService only when needed; bind API to loopback, never expose publicly. Use tonic/prost client from compatible Xray protobuf definitions. Runtime API updates must reconcile with persistent desired config; do not rely on ephemeral changes alone.
- traffic: calculate deltas safely when counters reset, use stable client identity mapping, aggregate and persist; quotas/expiry enforced by a clearly documented eventual-consistency policy.
- offline: keep last healthy config running. A disconnected agent must not disable Xray merely because server is unavailable.

For MVP, choose full config apply + validated restart for correctness. Add selective hot updates only after reliable config revisioning and tests.

## 7. Embedded React UI

Use React + TS + Vite + Ant Design, React Router, TanStack Query; Zustand only if shared client state becomes necessary. Pages:
1. Login / first setup
2. Dashboard (nodes online, resource summary, recent tasks)
3. Nodes (list, enroll command, status, metrics, revoke)
4. Node detail (Xray version, service state, actions, task history)
5. Inbounds (create/edit VLESS+REALITY, validation)
6. Clients (assignments, expiry, quota, traffic)
7. Settings (account, sessions, server settings)

Build output copied to `crates/server/web-dist` before `cargo build -p panel-server`. `rust-embed` embeds all files. Axum serves `/assets/*` with immutable caching, `index.html` with no-cache, correct MIME, SPA fallback only for known UI paths, 404 for missing assets, and 404 JSON for unknown API routes. Security headers and a strict CSP appropriate for AntD. Never expose private files via static routes.

## 8. Interactive installer and bootstrap

Installer is a third Rust binary (`panel-installer`), not a daemon. CLI:
- `panel-installer install [--component server|agent|all] [--non-interactive --config FILE]`
- `panel-installer upgrade [--component ...] [--version ...]`
- `panel-installer uninstall [--component ...] [--purge] [--remove-xray]`
- `panel-installer repair [--component ...]`
- `panel-installer status`

Interactive flow with clap + dialoguer:
1. Check TTY, root/sudo, Linux, architecture, systemd, connectivity, disk and existing installation.
2. Choose install/update/repair/uninstall.
3. Choose server, agent, or both.
4. Quick or custom mode.
5. Server: bind address, port, TLS cert/key or explicit local-only HTTP, admin account initialization, data directory, service autostart.
6. Agent: server URL, display name, one-time enrollment token, Xray install yes/no.
7. Validate values, show complete plan, confirm.
8. Download and cryptographically verify artifacts; install to staging and atomically activate; create service account, directories and systemd units.
9. Start and health-check; rollback if failed; write manifest and show status.

Suggested paths: `/usr/local/bin/panel-server`, `/usr/local/bin/panel-agent`, `/usr/local/bin/panel-installer`; `/etc/panel/{server,agent}.toml`; `/var/lib/panel/{server,agent}`; `/opt/panel/xray/versions/...`; `/etc/systemd/system/{panel-server,panel-agent,xray}.service`. Never delete unowned files. Separate normal uninstall (retain data) from purge (explicit confirmation); revoke node credentials before/after uninstall as connectivity permits. Server data purge is destructive and must require explicit typed confirmation.

Bootstrap shell script: download from a pinned GitHub Release, detect architecture, verify signature with a trusted embedded public key or an equivalent authenticated trust anchor, then execute installer in interactive TTY. Download-to-file-then-execute rather than `curl | bash` to preserve stdin. Provide safe unattended install separately. Ensure installer self-upgrade/uninstall is done by an external process, not a daemon deleting itself mid-operation.

Privileges: do not rely on a permanent root agent. Prefer systemd service hardening (`NoNewPrivileges`, `ProtectSystem`, `ProtectHome`, `ReadWritePaths`, capability restrictions) and a small root-owned helper/installer invoked through strictly allowlisted operations. Document how authorization is enforced and test escalation attempts.

## 9. HTTPS without Caddy

Axum with rustls. MVP supports user-provided certificate/key and local-only HTTP for initial development. Production-facing HTTPS is required for browser and Agent. Automatic ACME can be a later milestone; implementing certificate renewal and hot reload is separate from simply enabling rustls. Do not expose admin authentication over public HTTP. Ensure WSS uses TLS validation and certificate errors fail closed.

## 10. CI/CD and releases

CI on PR/push:
- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- `pnpm install --frozen-lockfile && pnpm run lint && pnpm run build` under web
- build server with copied dist and verify SPA assets are embedded
- test protocol schema compatibility and SQLite migrations
- dependency/security scans as feasible

Release on signed version tag:
1. Checkout, setup Node and the pinned pnpm version, `pnpm install --frozen-lockfile`, build React.
2. Copy web/dist to crates/server/web-dist.
3. Setup Rust, build server, agent, installer for Linux x86_64 and aarch64 (native runners or tested cross-compile).
4. Run tests and smoke tests.
5. Package binaries + service templates + bootstrap.
6. Generate checksums, sign artifacts using a verifiable release signing mechanism; publish verification instructions and trusted public key handling.
7. Upload assets to GitHub Release and attach release notes.

Never put signing private keys in repo. Prefer short-lived signing identities where possible. Pin GitHub Actions by full commit SHA for hardened production workflow. Avoid unsupported claims of reproducible builds unless verified.

## 11. Phased delivery and acceptance criteria

### Phase 0 — Repository bootstrap
- Create workspace, web scaffold, CI, format/lint/test scripts, README and architecture/security docs.
- Server starts, responds `/api/v1/health`, serves embedded React page.
- Agent CLI starts and prints version; installer CLI help works.
- Acceptance: clean checkout builds in documented order; no production Node dependency.

### Phase 1 — Server auth and SQLite
- Migrations, first admin bootstrap, login/logout/session cookie/CSRF, node CRUD, audit logging.
- Acceptance: auth tests, unauthorized access denied, migrations idempotent, secrets redacted.

### Phase 2 — Agent enrollment and reliable connection
- Single-use enrollment, persistent node identity, WSS, heartbeat, reconnection, task ACK/result, offline detection, deduplication.
- Acceptance: 2 agents connect; forced disconnect recovers; expired/reused token rejected; repeated task does not repeat side effect.

### Phase 3 — Linux metrics and systemd
- Metrics collection, node dashboard, allowlisted service status, privilege boundary and audit.
- Acceptance: real Linux node reports metrics, unauthorized systemd operation denied.

### Phase 4 — Xray installation and lifecycle
- Official verified binary download, versioned install, systemd unit, start/stop/restart/status, upgrade/rollback/uninstall.
- Acceptance: install fresh node, restart, rollback, do not touch pre-existing unowned Xray.

### Phase 5 — Xray config management
- Typed VLESS+REALITY inbound/client model, JSON generation, config validation, atomic apply, revisions, health-check, rollback.
- Acceptance: create inbound/client from UI, Xray config passes validation, service remains healthy, failed config rolls back.

### Phase 6 — Traffic and quotas
- Xray stats, counter delta accounting, aggregation, quotas/expiry, UI charts.
- Acceptance: controlled traffic test produces plausible nonnegative usage; restart/reset does not create negative or huge false deltas.

### Phase 7 — Interactive installer
- Bootstrap, TTY wizard, install/update/repair/uninstall/purge, manifest, systemd setup, rollback.
- Acceptance: fresh VM one-command bootstrap works; second install is safe; upgrade and uninstall preserve/remove exactly requested data.

### Phase 8 — Harden and release
- HTTPS, signed releases, ARM64, tests on clean Ubuntu/Debian VMs, logging, rate limits, CSP, backup/restore docs.
- Acceptance: no default credentials; no generic remote exec; HTTPS verified; release install tested on both architectures.

## 12. Testing matrix

- Unit: protocol serialization/version rejection, validators, Xray config generation, path traversal rejection, task idempotency.
- Integration: SQLite migrations, Axum auth/API, WebSocket enrollment/reconnect, static asset MIME/fallback.
- Linux VM: systemd service management, permissions, installer lifecycle, agent restarts, Xray config validation and rollback.
- E2E: browser login → node enroll → install Xray → add inbound/client → apply config → view status/traffic.
- Failure injection: corrupt download, disk full, port occupied, invalid config, agent offline, duplicate task, partial upgrade, interrupted installer, credential revoked.

## 13. Rules for Codex execution

1. First inspect the repo; if empty, start Phase 0. Write `docs/architecture.md`, `docs/security.md`, and a task checklist in `docs/progress.md`.
2. Implement **only one phase per iteration**. Before editing, list intended files and acceptance criteria.
3. Use real working code, not TODO stubs for critical paths. If an external system is unavailable, build a clearly labeled fake for tests only.
4. Run formatter, linter, tests and builds for changed components; report exact commands and results.
5. Update docs/progress.md after each phase with completed tasks, decisions, blockers and next phase.
6. Prefer simple code and minimal dependencies. Do not add Redis, Postgres, Node server, Caddy, containers, generic job queue, or microservices.
7. No arbitrary remote command execution or insecure TLS bypass, even for convenience.
8. Explicitly call out assumptions and tradeoffs. Avoid inventing Xray API capabilities; validate against pinned official Xray version/protos.
9. Keep commits logically scoped; do not move to next phase until acceptance criteria pass.
10. When uncertain, choose the smallest secure implementation and document the alternative.
